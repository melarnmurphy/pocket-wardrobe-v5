Garment split and cut-out

How one photo becomes one or more wardrobe pieces, each with a transparent cut-out, a category, a colour and a fabric guess. This is the pipeline behind screens 14a and 14b in the phone mockups, w1a and w1d on desktop, and the press-and-hold lift in the cut-outs prototype. Written for an engineer or a coding agent to implement directly.

runs
on device first, server as fallback
budget
≤ 1.2s per photo, 12 photos in parallel batches of 3
never blocks
user can leave; work resumes in background

The sequence

Every step names its actor, its input and its output. Steps 2–5 are the ones worth getting right; the rest is plumbing.

1
Intake
Client. Multi-select from the library, live camera capture, a pasted transparent PNG, or a drag-and-drop folder on desktop. Accept HEIC, JPEG, PNG, WebP. Downscale the working copy to 1600px on the long edge; keep the original for re-processing.
out: Upload[] { id, originalUri, workingUri, exifDate?, source: library|camera|paste|drop }
2
Instance segmentation — how many garments?
Ask for all foreground instances, not one subject. On iOS 17+ that is Vision's foreground instance mask request, which returns an instance count and a per-instance mask. On the web, run a segmentation model server-side (SAM-family or a garment-tuned equivalent) behind one endpoint. Discard instances under 3% of frame area or with fewer than 400px of mask width — those are jewellery, hardware and shadow.
out: Instance[] { maskUri, bbox, areaRatio, confidence }
One instance is the common case (a garment on a hanger). Two or three means a worn outfit — that is what triggers the split prompt in 14b. More than four almost always means a cluttered background: fall back to single-subject lift and let the user crop.
3
Body-part split when instances are fused
A person wearing an outfit usually returns as one instance. Split it with a human-pose estimate: shoulders, hips, knees, ankles. Cut top from bottom at the hip keypoint, footwear at the ankle keypoint, outerwear from the top only if the pose model reports layered edges. Never cut on fixed percentages — that is what the mockups do (band crops at 0.155–0.475 and so on), and it is only acceptable for static artwork.
out: GarmentCandidate[] { maskUri, bbox, slot: top|bottom|dress|outer|shoe|bag, sourceInstanceId }
4
Matte and export
Feather the mask edge by 1–2px, erode 1px to kill background fringe, then composite to a premultiplied PNG with an alpha-tight bounding box and 4px of padding. Store at two sizes: 1200px long edge for detail views, 400px for grids. Keep the mask so a cut can be redone without re-segmenting.
out: Cutout { pngUri, pngThumbUri, maskUri, width, height, alphaBbox }
Sheer fabric is the hard case. Chiffon and mesh carry partial alpha; do not threshold the mask to binary or the garment turns into a silhouette. The blouse in the mockups is the test image.
5
Attributes — category, colour, fabric
Run one vision-language pass per cut-out and ask for a constrained JSON answer against our own taxonomy — free-text labels will not join to the filter set. Colour comes from the mask's dominant cluster mapped to the ten wardrobe colours, not from the model's prose. Fabric is a guess and must be labelled as one: below 0.6 confidence, render the dashed "fabric?" chip from 14b rather than a wrong answer.
out: Attributes { category, subcategory?, colour, colourHex, fabric?, fabricConfidence, season[], name }
6
Duplicate check
Embed each cut-out and compare against the existing wardrobe by cosine similarity within the same category and colour. Above 0.92, show the side-by-side "you may already own this" dialog from 14a. Never merge silently — people own two of the same white shirt.
out: DuplicateHint? { pieceId, similarity }
7
Review, then commit
Nothing enters the wardrobe until the user confirms the batch (14b, and the desktop table in w1d). Editing a row writes back to the candidate, not to the wardrobe. On commit, create Piece records, attach cut-outs, and leave price null — prices arrive later from a store connection or a receipt, and a null price must render as "add later", never as A$0.
out: Piece[] { id, name, category, colour, fabric?, cutoutUri, price: null, addedAt, availability: "wearable" }

Rules that are product decisions, not engineering ones

·A photo never enters the wardrobe unreviewed. Batch of one included.
·A guess the machine is unsure of is shown as a question, never as a fact.
·Price stays null until it comes from a receipt, a store, or the user. Cost per wear hides rather than lying.
·Photos and masks are processed on device where the platform allows it; anything sent to a server is deleted within 30 days, and the copy says which is which.
·Splitting is offered, not imposed. Some people think in outfits.

Done means

1
Twelve library photos become twelve reviewable candidates in under fifteen seconds on a three-year-old phone.
2
A full-length outfit photo proposes the right number of garments, and the hip and ankle cuts land on the garment edge, not mid-thigh.
3
A sheer garment keeps its transparency, and a white garment on a white wall still separates.
4
Leaving the screen mid-batch loses nothing, and returning shows what finished.
